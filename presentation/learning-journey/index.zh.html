第一天
第一层

提示词（简单提问）

就像给一个知识渊博的朋友发短信 — 你问一个问题，他们会给你一个答案。但你不知道他们是怎么得到答案的。

大局观

你已经安装了 Claude Code。接下来做什么？

第一天涵盖三个基础层级 — 每一层都让你对如何让 Claude 工作有更多控制。

把它想象成招聘

每一层都代表着你对关系信任度和结构化程度的提升。

1
提示词 向街头的陌生人问路
2
Agent 聘请一位以特定方式做事的专家
3
技能 该专家针对特定任务有专门的培训

提示词实战

打开终端，输入 claude。你现在处于一个对话中。试着输入：

what is the weather in Karachi?

Claude 会回答 — 但如何回答是不可预测的。它可能会：

  • 从训练数据中提取（可能是过时的）
  • 搜索网络（如果有网络工具可用）
  • 给出一个通用答案而不是实时数据

局限性

每次你问"天气怎么样？"，Claude 可能以不同的方式获取数据 — 或者根本不获取真实数据。它使用相同来源或方法没有任何保证。

何时提示词效果最好

提示词非常适合快速的一次性问题！

🔍
询问代码库相关问题 "这个文件是做什么的？"
✏️
编写或编辑文档 "把这封邮件改得更专业一些"
💡
头脑风暴 "给我这个活动的5个主题行"
💬
解释事物 "像我不是开发者一样解释这个错误信息"

要点

要获得一致、可靠的结果，仅靠提示词是不够的。你需要更多控制。

第二层

Agent（专业人士）

Agent 是 Claude 扮演的特定角色 — 就像分配一个职位头衔。

餐厅厨房

这样理解

没有 Agent，你走进一个随机的厨房，喊"给我做意面！"— 听到的人可能煮方便面，也可能做一顿五道菜的意大利大餐。

没有 Agent

你问 Claude："迪拜天气怎么样？"

它可能查训练数据、搜索网络，或者凭猜测回答。

你不知道它会做什么。

有 Agent

weather-agent 有明确的工作描述：

"始终从 Open-Meteo API 获取迪拜数据。始终以特定格式返回温度。"

同样的问题，同样的方法，每次都一样。

提示词 vs. Agent

使用 Agent 时会发生什么变化 — 以本仓库中的 weather-agent 为真实示例：

提示词 Agent
数据源 可能是任何地方 始终是 Open-Meteo API
位置 Claude 随意选择 始终是迪拜（纬度：25.2，经度：55.3）
格式 随机段落 简洁的温度+单位
一致性 每次都不同 同样的方法，每次都一样

要点

Agent 给你可预测性。同样的问题 → 同样的方法 → 同样的质量。不是更聪明 — 是一致。

第三层

技能（培训手册）

技能是 Agent（或 Claude 本身）可以使用的特定能力 — 就像新员工的操作手册。

培训手册

这样理解

当有人加入你的团队时，他们有一个角色（Agent），但他们也会参加特定的培训模块 — 如何使用 CRM、如何写提案、如何主持站会。每个培训模块就是一个技能。

一个真实人物示例

Shayan 有很多技能：

💻
工程技能 会写代码
🎮
游戏技能 了解游戏机制
📖
阅读技能 能够消化和总结长文档

每个技能都有自己的知识和方法。Shayan 根据任务选择正确的技能。Claude 也是一样。

为什么分离 Agent 和技能？

Agent = 这个人

weather-agent 是职位头衔为"天气预报员"的人。

它定义了角色和行为。

技能 = 培训

weather-fetcher 技能是关于如何获取天气数据的具体培训。

它包含精确的说明：

  • 调用这个特定的 API URL
  • 从特定字段提取温度
  • 以特定格式返回

优势

一个 Agent 可以有多个技能，一个技能也可以被多个 Agent 使用。技能是可复用的构建块。Agent 是使用它们的人。

第一天总结

综合运用

三个层级，每个层级都增加了对 Claude 工作方式的控制。

三个层级

第一层：提示词 你 → "天气怎么样？" → Claude 想办法搞定 （不可预测的方法） 第二层：AGENT 你 → 天气 Agent → 始终使用相同方法 （可预测的方法） 第三层：技能 你 → 天气 Agent → 使用天气获取技能 （带有具体指令的可预测方法）
层级 你控制什么 适用于
提示词 问题 快速的一次性问题
Agent 问题 + 谁来回答 可重复的任务
技能 问题 + 谁来回答 + 如何执行 关键工作流

第一天完成

你已经理解了这三个层级：提示词、Agent、技能。

在第一层多花时间 — 只需要提示。在终端中习惯向 Claude 提问。你用得越多，就越会注意到哪些任务会从 Agent 中受益。

明天：我们来构建它们。

第二天
第四层

项目记忆

在构建 Agent 和技能之前，Claude 需要了解你的项目。这从 CLAUDE.md 开始。

CLAUDE.md — 项目的大脑

这样理解

当新人加入你的团队，他们不会直接开始工作 — 他们会阅读团队 Wiki、README、入职文档。CLAUDE.md 就是 Claude 的入职文档。

它是项目根目录下的一个 markdown 文件，告诉 Claude：

1
项目是什么 "这是一个 FastAPI 后端 + React 前端的项目"
2
如何在其中工作 "使用 pytest 进行测试，遵循现有的路由模式"
3
避免什么 "永远不要直接修改 auth 中间件"

快速开始

在 Claude Code 中运行 /init 来为你的项目自动生成 CLAUDE.md。

CLAUDE.md 包含什么

# CLAUDE.md ## 项目概览 这是一个带有 FastAPI 后端和 React 前端的 TodoApp。 ## 关键命令 - npm run dev # 启动前端 - uvicorn main:app # 启动后端 - pytest # 运行测试 ## 架构 - 路由遵循 routes/todos.py 中的模式 - 前端组件使用 Tailwind CSS - 测试镜像源目录树：tests/test_*.py ## 规则 - 始终为新端点编写测试 - 使用现有的 Sidebar 组件进行导航 - CLAUDE.md 保持在 200 行以内

保持简短

目标控制在 200 行以内。超过 200 行的文件会消耗更多上下文，可能降低遵从度。将详细说明放在 .claude/rules/ 中。

记忆如何加载

Claude Code 使用两种机制来查找 CLAUDE.md 文件：

祖先加载（向上）

启动时，Claude 从当前目录向上遍历，加载找到的每个 CLAUDE.md。

始终立即加载。

后代加载（向下）

当前目录下方子目录中的 CLAUDE.md 是惰性加载的 — 只有当 Claude 读取这些文件夹中的文件时才会加载。

按需加载。

# 示例：从 /myapp 运行 `claude` /myapp/ CLAUDE.md # 启动时加载（当前目录） frontend/ CLAUDE.md # 当你操作 frontend/ 文件时加载 backend/ CLAUDE.md # 当你操作 backend/ 文件时加载

规则目录

对于特定主题的说明，使用 .claude/rules/*.md。每个规则文件可以使用顶部的 # Glob: pattern 来定位特定文件模式 — 它们只在与匹配文件一起工作时才加载。

第五层

构建技能与 Agent

现在 Claude 已经了解了你的项目，让我们赋予它专业能力。

创建你的第一个技能

技能位于 .claude/skills/<name>/SKILL.md。这是一个带有 YAML 头部的 markdown 文件。

# 文件：.claude/skills/weather-fetcher/SKILL.md --- name: weather-fetcher description: 从 Open-Meteo API 获取迪拜当前温度 user-invocable: false --- # 天气获取器 获取迪拜当前温度： 1. 调用 Open-Meteo API： https://api.open-meteo.com/v1/forecast ?latitude=25.2048&longitude=55.2708¤t=temperature_2m 2. 从响应中提取 current.temperature_2m 3. 返回："迪拜的温度是 {value}{unit}"

关键洞察

技能包含指令，而不是代码。它告诉 Claude 如何使用现有工具（如 WebFetch）做某事。把它想象成食谱，而不是程序。

技能头部字段

SKILL.md 顶部的 YAML 控制技能的行为：

name 显示名称和 /斜杠命令。默认为目录名
description 推荐 技能的作用 — 显示在自动完成中，用于自动发现
user-invocable 设为 false 可从 / 菜单隐藏 — 成为后台知识
allowed-tools 技能激活时允许使用而无需权限提示的工具
model 使用的模型：haiku、sonnet 或 opus
context 设为 fork 可在隔离的 subagent 上下文中运行

使用技能的两个方式

用户可调用：出现在 / 菜单中，用户直接运行。Agent 预加载：设置 user-invocable: false，然后在 agent 的 skills: 字段中列出 — 它成为注入到该 agent 的领域知识。

创建你的第一个 Agent

Agent 位于 .claude/agents/<name>.md。同样的模式 — 带有 YAML 头部的 markdown。

# 文件：.claude/agents/weather-agent.md --- name: weather-agent description: PROACTIVELY 获取迪拜、阿联酋的天气数据 model: sonnet tools: WebFetch, Read skills: - weather-fetcher color: green --- 你是一位迪拜的天气数据专家。 使用你预加载的 weather-fetcher 技能获取 当前温度并简洁地返回。

发生了什么

Agent 有：角色（天气专家）、受限工具（只有 WebFetch 和 Read）、预加载技能（weather-fetcher）、和特定模型（sonnet，节省成本）。

Agent 头部字段

agent 文件顶部的 YAML 控制其身份和能力：

name 推荐 唯一标识符 — 如果省略则默认为文件名
description 必需 何时调用。使用 "PROACTIVELY" 进行自动调用
model haiku、sonnet、opus 或 inherit（默认）
tools 工具白名单。省略则继承所有工具
skills 启动时预加载到 agent 上下文的技能名称列表
maxTurns Agent 停止前的最大轮次
memory 持久化记忆：user、project 或 local
color 任务列表中的视觉颜色：red、blue、green 等

Agent vs. 技能 — 存放位置

# 你的项目结构 myproject/ .claude/ agents/ # Agent 定义 weather-agent.md # 这个人（角色+行为） code-reviewer.md # 另一个 agent skills/ # 技能定义 weather-fetcher/ # 每个技能是一个文件夹 SKILL.md # 培训内容（指令） weather-svg-creator/ SKILL.md commands/ # 斜杠命令 rules/ # 条件指令 settings.json # 团队设置 CLAUDE.md # 项目记忆
Agent 技能
位置 .claude/agents/*.md .claude/skills/*/SKILL.md
是什么 带有行为的角色 任务指令
运行于 自己独立的隔离上下文 内联或分叉上下文
有工具？ 是 — 自有工具白名单 使用父级的工具
比喻 员工 培训手册

如何使用你的 Agent

一旦你创建了 agent 文件，Claude 可以自动调用它（如果描述中有 PROACTIVELY），或者你可以让 Claude 使用它：

# 在 Claude Code 对话中： 使用 weather-agent 获取迪拜当前的温度

在幕后，Claude 调用 Agent 工具：

# Claude 内部所做的 Agent( subagent_type = "weather-agent", description = "获取迪拜温度", prompt = "获取摄尔修斯温度" )

这样理解

你是经理。你说"给我天气。"Claude 派遣 weather-agent（专家）到他们自己的工作空间。Agent 使用他们的培训（weather-fetcher 技能）来完成工作。他们带着答案回来。

第六层

命令与编排

命令是将 Agent 和技能绑定到完整工作流的入口点。

命令 — 入口点

这样理解

如果 Agent 是员工，技能是他们的培训，那么命令就是经理手册 — "当有人要求天气报告时，首先问他们用摄氏度还是华氏度，然后派遣天气团队，然后创建可视化。"

命令位于 .claude/commands/<name>.md：

# 文件：.claude/commands/weather-orchestrator.md --- description: 获取天气并创建 SVG 卡片 model: haiku --- 1. 问用户：摄氏度还是华氏度？ 2. 使用 weather-agent 获取迪拜的温度 3. 使用 weather-svg-creator 技能创建 SVG 卡片 4. 向用户展示结果

如何运行

在 Claude Code 中输入 /weather-orchestrator。命令编排整个工作流。

命令 → Agent → 技能

这是 Claude Code 工作流的核心架构模式：

编排流程 /weather-orchestrator 命令（入口点） | 步骤 1：问用户 C/F？ | 步骤 2：Agent 工具 | v weather-agent Agent（专家） skill: weather-fetcher 技能（预加载培训） tools: WebFetch, Read | 返回：温度 + 单位 | 步骤 3：Skill 工具 | v weather-svg-creator 技能（直接调用） | 创建：weather.svg + output.md

使用技能的两种方式

天气工作流展示了单一流程中的两种技能模式：

模式 1：Agent 技能（预加载）

weather-fetcher 列在 agent 的 skills: 字段中。

它的完整内容在启动时注入到 agent 的上下文中。Agent 像参考手册一样阅读它。

# 在 weather-agent.md 中 skills: - weather-fetcher

模式 2：直接调用

weather-svg-creator 通过 Skill 工具由命令直接调用。

它独立运行在命令的上下文中，而不是在任何 agent 内部。

# 在命令提示中 Skill(skill: "weather-svg-creator")

第二天总结

今天你学习了如何构建各个部分并将它们连接在一起：

组件 位置 用途
CLAUDE.md 项目根目录 项目记忆 — 告诉 Claude 关于你的代码库
规则 .claude/rules/*.md 由文件模式触发的条件指令
技能 .claude/skills/*/SKILL.md 可复用指令 — 培训手册
Agent .claude/agents/*.md 具有角色、工具和预加载技能的专业人员
命令 .claude/commands/*.md 将 Agent 和技能编排成工作流的协调器

架构

命令（入口点） → Agent（带技能的专家） → 技能（可复用指令）。每一层都增加了结构和可预测性。
