# 🔥 Claude Code Ops 4.6 分析。高推理

当 Anthropic 发布像 Opus 4.6 这样的模型时，**模型权重**——数十亿学习参数——是冻结的。训练非常昂贵（数百万美元，数周计算）。没有人会在一夜之间重新训练模型。

但权重只是更大系统中的一层。研究揭示了至少 **7 种不同的机制**，即使模型权重冻结，也可能导致真实或感知的质量变化。

| 问题 | 回答 |
|----------|--------|
| 模型权重在发布后会改变吗？ | **不会** — 所有提供商确认 |
| 模型是否可能日复一日表现不同？ | **是的** — 已证明有 ±8-14% 的差异 |
| 是故意"削弱"吗？ | **不是** — 没有故意退化的证据 |
| 基础设施错误是真实的吗？ | **是的** — Anthropic 确认了 3 个影响高达 16% 请求的错误 |
| 部分是心理因素吗？ | **是的** — 确认偏差和蜜月效应是真实的 |
| 系统提示/后训练可以改变吗？ | **是的** — 跨提供商记录 |
| 用户应该信任他们的感知吗？ | **部分** — 真实原因存在，但感知放大了它们 |

## 完整推理堆栈

模型权重是冻结的，但**其上的九层**可以独立影响你体验到的内容：

```
┌──────────────────────────────────────────────┐
│  你的会话上下文                               │  ← 在会话内退化
│  （累积的错误、长对话）                       │
├──────────────────────────────────────────────┤
│  系统提示                                     │  ← 定期更新
│  （安全规则、行为指令）                       │
├──────────────────────────────────────────────┤
│  后训练（RLHF / 微调）                        │  ← 可以静默更新
│  （指令遵循、安全对齐）                       │
├──────────────────────────────────────────────┤
│  采样参数                                     │  ← 可以在服务端调整
│  （temperature、top-p、top-k）                │
├──────────────────────────────────────────────┤
│  推测解码                                     │  ← 草稿模型质量变化
│  （草稿模型预测 + 验证）                      │
├──────────────────────────────────────────────┤
│  MoE 路由 / 批次组成                          │  ← 已证明 ±8-14% 差异
│  （每个请求激活哪些专家）                     │
├──────────────────────────────────────────────┤
│  硬件路由                                     │  ← TPU vs GPU vs Trainium
│  （哪个集群服务你的请求）                     │
├──────────────────────────────────────────────┤
│  量化级别                                     │  ← 可能在负载下变化
│  （FP16 vs INT8 vs INT4 精度）               │
├──────────────────────────────────────────────┤
│  编译器和运行时                               │  ← XLA 错误已证实真实
│  （XLA:TPU、CUDA、硬件特定代码）              │
├──────────────────────────────────────────────┤
│  模型权重（冻结）                             │  ← 这些不会改变
│  （数十亿学习参数）                           │
└──────────────────────────────────────────────┘
```

关键心智模型：**冻结权重 ≠ 冻结行为**。这就像说"相同引擎 = 相同驾驶体验"，却忽略了轮胎、道路状况、燃油质量和驾驶员疲劳。

## 已证实的原因：基础设施错误

### Anthropic 2025 年 9 月的事后分析

2025 年 9 月，Anthropic 发布了详细的事后分析，揭示了**三个独立的基础设施错误**，在 2025 年 8 月至 9 月间降低了 Claude 的质量。他们的官方声明：

> "我们从不因需求、时间或服务器负载而降低模型质量。用户报告的问题完全是由基础设施错误造成的。"

### 错误 #1 — 上下文窗口路由错误

Sonnet 4 请求被错误地路由到配置为 1M token 上下文窗口的服务器，而不是标准服务器。

- **时间线**：8 月 5 日引入，8 月 29 日负载均衡更改后恶化
- **峰值影响**：最严重时 16% 的 Sonnet 4 请求受影响（8 月 31 日）
- **用户影响**：约 30% 的 Claude Code 用户至少有一条降级消息
- **隐蔽细节**：路由是"粘性"的——一旦你遇到坏服务器，后续请求会继续去那里
- **修复**：9 月 4-18 日（跨平台推出）

### 错误 #2 — TPU 输出损坏

TPU 服务器上的配置错误导致 token 生成期间的错误，为不应该出现的 token 分配高概率。

- **症状**：英文响应中间出现泰语或中文字符，明显的代码语法错误
- **受影响**：Opus 4.1 和 Opus 4（8 月 25-28 日），Sonnet 4（8 月 25 日-9 月 2 日）
- **范围**：仅 Claude API；第三方平台不受影响
- **修复**：9 月 2 日回滚

### 错误 #3 — XLA:TPU 编译器错误编译（最棘手的）

修复精度问题的代码更改意外暴露了 Google XLA:TPU 中的**潜在编译器错误**。

- **根本原因**：近似 top-k 操作（用于选择最可能的下一个 token）"有时返回完全错误的结果，但仅对某些批次大小和模型配置"
- **为什么难以发现**：它的行为会根据之前或之后运行的操作以及是否启用调试工具而改变
- **隐藏数月**：2024 年 12 月的先前变通方案意外掩盖了这个更深的错误
- **受影响**：Haiku 3.5 已确认；Sonnet 4 和 Opus 3 的子集疑似
- **解决方案**：从近似 top-k 切换到精确 top-k；接受"轻微效率影响"，因为"模型质量是不可妥协的"

### 为什么检测困难

Anthropic 自己的自动评估没有捕捉到用户报告的退化，"部分原因是 Claude 通常能很好地从孤立错误中恢复"。每个错误在不同平台以不同速率产生不同症状，造成"令人困惑的报告混合，不指向任何单一原因"。

关键背景：Claude 在**三种不同硬件平台**上运行（AWS Trainium、NVIDIA GPU、Google TPU），每种都有不同的故障模式、编译器和精度行为。你的请求可能在不同日期遇到不同硬件。

## 已证实的原因：MoE 路由差异

现代大型模型通常使用**混合专家（MoE）**架构，其中只有模型参数的子集（"专家"）为每个输入激活。一个学习的路由器决定使用哪些专家。

Scale AI 的研究揭示了一个关键发现：

> "稀疏 MoE 和批量推理的组合会产生不可预测的结果，因为批次的组成可以决定你的查询被路由到哪个专家，而同一批次中其他用户的查询混合是不确定的。"

### 跨提供商测量的日间差异

| 提供商 | 日间得分差异 |
|----------|--------------------------|
| OpenAI（GPT-4 变体） | ±10–12% |
| Anthropic（Claude 变体） | ±8–11% |
| Google（Gemini 变体） | ±9–14% |

具体例子：同一模型在某天在越狱抵抗上得分 **77%**，第二天得 **63%**。相同的模型、相同的权重、相同的测试——仅因基础设施就有 14 个百分点的波动。

这意味着即使零错误和零更改，同一模型也可能在不同日子产生明显不同的质量输出，纯粹由于请求如何批处理和路由。当日常噪声为 10-15% 时，A/B 测试无法可靠检测 5% 的质量信号。

## 已证实的原因：系统提示和后训练更新

### 系统提示更改

模型权重不变，但包装这些权重的**系统提示**可以随时更新。对 Claude 系统提示演变的分析显示数十次迭代，"热修复"——添加以修补不良行为的短指令——定期添加和删除。

Claude 3.7 的系统提示包含多个针对常见 LLM "陷阱"的热修复指令。Claude 4.0 的系统提示删除了所有这些，行为通过强化学习在后训练中解决。

### 后训练理论

无法解释的质量转变最合理的理论：公司可以在不改变基础模型权重的情况下更新**微调和 RLHF**（人类反馈强化学习）。这在技术上使得"模型没有改变"的说法是真实的，同时仍通过更新的安全护栏和指令遵循调整改变行为。

## 已证实的原因：静默模型切换

OpenAI 已被多次记录静默更改用户交互的模型：

- 一夜之间删除模型选择器，强制用户从 GPT-4o 切换到 GPT-5
- 使 GPT-4o 成为需要在设置中手动切换的隐藏"传统模型"，没有应用内通知
- "自动切换器"错误将用户路由到错误的模型
- Plus 订阅者报告模型未经同意切换到"受限版本"

Sam Altman 承认推出"比我们希望的要颠簸一些"。Reddit 帖子获得数千点赞，称新模型是"灾难"和"降级"。

这证明了模型切换**确实发生**在行业中——有时是故意的（产品决策），有时是意外的（路由错误）。

## 促成因素

### 负载下量化

为了经济高效地服务数百万用户，公司可能提供**量化**版本的模型——将精度从 FP16 降低到 INT8 或 INT4。这可以将内存使用减少 2-4 倍并加速推理，但引入微妙的质量损失。提供商是否在负载下动态切换量化级别尚有争议，但这种技术能力存在，并在 vLLM 和 TensorRT 等服务框架中有详细记录。

### 推测解码

现代服务堆栈使用较小的"草稿"模型提前预测多个 token，然后让真正的模型验证它们。理论上这保持相同的输出分布，但实际上接受率因领域和上下文而异。开箱即用的草稿模型在某些情况下可能工作良好，但通常在特定领域任务或非常长的上下文中挣扎。

### 上下文窗口污染

在长编码会话中，早期错误在上下文中累积。模型看到自己的错误并可能延续它们。这是单会话中"Claude 变笨"的最常见原因——不是模型退化，而是上下文污染。

**实用提示**：当质量感觉不对时使用 `/compact` 或开始新会话。这是你能做的最可行的事情。

## 斯坦福研究 — 以及为什么它很复杂

2023 年斯坦福和 UC Berkeley 的里程碑研究（Chen, Zaharia, Zou）——"ChatGPT 的行为如何随时间变化？"——经常被引用为 LLM 退化的证据。标题发现：

> GPT-4 在"这个数字是质数吗？逐步思考"上的准确率从 2023 年 3 月到 6 月从 **97.6% 下降到 2.4%**。

### 研究证明了什么

- "相同" LLM 服务的行为**可能在短时间内大幅改变**
- 不同能力可能朝相反方向移动（GPT-4 数学变差，GPT-3.5 变好）
- 代码生成质量下降（GPT-4 可执行代码：52% → 10%）
- 该研究创造了术语 **"LLM 漂移"**

### 方法论批评

- 3 月版本使用 **temperature 0.0** 而 6 月版本使用 **temperature 1.0** — 一个根本的混杂变量，增加随机性
- 每个任务只有 **500 个查询** — 对确定的统计主张来说太小
- "数学问题"实际上是是/否问题，模型的猜测模式改变了，而不是数学能力
- 更改可能反映了有意的**后训练安全更新**，而非意外退化

该研究证明了一些重要的东西——LLM 行为随时间变化——但机制可能是有意的更新，而非意外退化。

## 心理学

### 确认偏差

一旦有人发推"Claude 今天很蠢"，你就开始注意到每个错误。在没人抱怨的日子里，你忽略同样的错误。社交媒体放大了这种效应。

### 蜜月效应

用户在新模型上经历初始蜜月期，然后逐渐发现限制。模型没有改变——期望比能力更快向上调整。

### 任务难度差异

你的任务日复一日变化。一整天难题感觉像模型变差了，即使没有。

### "周末 Claude" 神话

尽管许多用户相信星期几的模式，但严格分析发现**没有一致的证据**支持星期几的质量模式。一篇题为"AI 在周一更笨"的分析一无所获。

### LLM 的随机性质

LLM 是概率性的。相同提示每次可能产生不同输出。在运气不好的连续中，你可能连续得到几个糟糕的响应——纯粹是随机性，不是退化。

## 底线

用户描述的现象是**真实但归因错误**：

- **正确**：他们在某些日子的体验确实退化了
- **不正确**：模型被故意"削弱"

实际原因是以下组合：

1. **基础设施错误** — Anthropic 事后分析证实（高达 16% 的请求受影响）
2. **MoE 路由差异** — Scale AI 测量的 ±8-14% 质量波动，即使零更改
3. **系统提示和后训练更新** — 跨提供商记录
4. **硬件异构性** — TPU vs GPU vs Trainium，每种都有不同的故障模式
5. **上下文污染** — 长会话降低会话内质量
6. **确认偏差** — 社交媒体放大感知模式
7. **随机差异** — 相同模型、相同提示、每次不同输出

测量问题很严重：±8-14% 的日间差异意味着你无法从噪声中区分真正的 5% 质量变化。这就是为什么"都是你的幻觉"和"他们削弱了它"两派都感到自信——信噪比使得无法仅从个人经验判断。

# 🔥 Codex 5.3 高推理和发现

### 报告范围

本节解释为什么用户可能会经历 Claude 输出质量下降的短窗口期，而 Codex 5.3 在编码任务上感觉稳定或更强。重点不是永久模型质量排名。重点是实际服务条件下的短视界生产行为。

报告日期：2026 年 3 月 5 日。

### 观察到的模式

报告的模式是：

1. 模型质量在一段时间内可接受。
2. 质量似乎退化几天。
3. 质量恢复接近之前的基线。

这种形状通常是服务堆栈或推出模式，而不是永久基础模型能力变化。永久能力下降通常不会在没有明确回滚或修复的情况下如此快恢复。

### 高推理：为什么 Codex 5.3 在糟糕窗口期可能看起来更好

Codex 5.3 可以在另一个提供商的退化期间明显更强，原因有几个技术原因，它们可能同时发生：

1. 产品目标契合。Codex 5.3 针对代码生成和代理编码工作流进行了优化，因此即使原始模型强度相等，由于工具编排、仓库推理和以代码为中心的指令调优，也可以产生更好的编码结果。
2. 推理策略差异。提供商独立调整延迟、推理深度和解码默认值。一个提供商更保守的策略在同一天可能比另一个提供商激进的速度优化策略看起来"更聪明"。
3. 服务路径分离。即使两个提供商托管最先进的模型，它们运行不同的路由层、编译器/运行时堆栈和推出管道。一个堆栈中的事故并不意味着另一个堆栈中的相关退化。
4. 推出和回滚时机。如果一个提供商正在推出中间而另一个稳定，用户可能会看到大的临时质量分歧，而模型权重没有潜在的长期变化。
5. 会话级污染效应。在长编码聊天中，错误累积可以放大感知下降。竞争助手可能感觉更好，仅仅因为失败的会话被重置或因为其工具循环恢复更快。

### 详细发现

对于像"Claude 感觉很弱大约四天，然后回来了"这样的报告，最可能的解释是：

1. 提供商端事故、路由问题、解码/运行时错误或推出回归影响了请求子集。
2. 问题持续足够长，在真实工作流中被重复注意到。
3. 问题被修复或回滚。
4. 感知质量快速返回。

在同一时期，Codex 5.3 可能感觉明显更好，因为它没有共享相同的事故路径，也因为编码任务优化放大了实际结果差距。

### 此模式的假设排名

| 假设 | 可能性 | 理由 |
|------------|------------|-----------|
| 提供商事故加回滚 | 高 | 最匹配多天下跌后快速恢复 |
| 服务配置更改（采样/延迟/推理预算） | 高 | 无需模型重新训练的突发行为转变常见来源 |
| 静默别名或快照移动 | 中高 | 可以在无可见用户操作的情况下改变行为 |
| 仅提示漂移和上下文污染 | 中 | 可以降低会话，但不太可能单独解释广泛的多天报告 |
| 永久基础模型退化 | 低 | 与快速返回先前质量不一致 |

### 什么会证实或证伪这一发现

要将此从高置信度推断转化为硬证明，需要跨天收集相同任务集的请求级遥测：

1. 请求时的确切模型标识符和快照/别名。
2. 提供商公开的任何后端指纹或发布标记。
3. 解码参数（temperature、top_p、top_k、max tokens）。
4. 延迟、超时和错误率跟踪。
5. 固定编码基准提示集上的结构化质量分数。
6. 失败点的会话长度和 token 上下文深度。

如果质量下降与事故窗口、配置更改或后端指纹转变相关，则事故/配置假设得到确认。如果不存在这种转变且退化仅在长会话中，上下文污染成为主要解释。

### 实用工程指导

为了减少生产中的日间差异：

1. 如果可用，固定模型快照而不是使用浮动别名。
2. 存储请求元数据（模型 ID、参数、延迟、错误、响应质量标签）。
3. 为编码任务运行固定的每日金丝雀套件并对回归发出警报。
4. 在多次失败回合后重置或压缩长时间运行的会话。
5. 为事故窗口保留备用提供商/模型路径。
6. 在内部仪表板中分离"模型质量"和"服务可靠性"。

### 最终结论

Codex 5.3 在短期 Claude 退化窗口期间看起来更好是现代 LLM 运营中技术上合理且预期的结果。最强的解释不是永久模型崩溃。最强的解释是一个提供商的临时服务路径退化，结合同一时期另一个提供商的编码特定优化和稳定运行。
